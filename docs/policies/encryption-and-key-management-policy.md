# Encryption and Key Management Policy

- **Next review:** [Review Date]
- **Version:** 1.0

## Purpose

This policy sets how [Company] encrypts customer information in transit and at rest, and how
encryption keys and other secrets are created, used, rotated and retired.

## Scope

All production systems that store or move customer information, all encryption keys (AWS KMS
keys, field data keys, signing keys, the password pepper), and all secrets (database passwords,
API keys, webhook secrets, OAuth client secrets).

## Policy

### 1. Approved algorithms

| Use                          | Required                                                            |
| ---------------------------- | ------------------------------------------------------------------- |
| Transport                    | TLS 1.2 or later; TLS 1.3 preferred; no SSL, TLS 1.0 or 1.1         |
| Field encryption             | AES-256-GCM, random 96-bit IV, with additional authenticated data   |
| Key wrapping                 | AWS KMS symmetric keys (AES-256, FIPS 140 validated HSMs)           |
| Password hashing             | argon2id with a server-side pepper                                  |
| Token storage                | Only the SHA-256 hash of session and one-time tokens is stored      |
| Signing (links, OAuth state) | HMAC with a dedicated 256-bit signing key, never the encryption key |

Custom cryptography is not allowed. Use `packages/crypto` and the platform's libraries.

### 2. Encryption in transit

1. All external traffic must use HTTPS. Plain HTTP may only redirect to HTTPS. Cookies must be
   `Secure`, and production refuses to start without it (`apps/api/src/config.ts`).
2. Connections that leave a host must use TLS with the server verified. In production the API
   requires `sslmode=verify-full` to Postgres and `https://` for the web origin, S3 endpoint,
   exchange-rate source and bank feed webhook URL (`apps/api/src/config.ts`).
3. The virus scanner speaks plain TCP, so it must run on the same host as the API (a sidecar);
   production refuses a remote scanner host.
4. TLS certificates must be issued and renewed automatically (AWS Certificate Manager) and
   monitored for expiry.

### 3. Encryption at rest

1. **Field encryption:** these values must be encrypted in the application before they are stored:
   SSNs, EINs, TINs, bank account numbers, MFA secrets, third-party access and refresh tokens
   (Plaid, Intuit), and the data keys of stored files and data exports. Each value is bound to its
   row and field by its AAD, so a value copied to another row does not decrypt (ADR 0004). The
   list of encrypted columns is `ENCRYPTED_COLUMNS` in `apps/api/src/security/rotation.ts`; a
   test checks it against the schema.
2. **Masking:** where display or search needs it, only a non-sensitive projection (for example,
   the last four digits) is stored in clear. Revealing a full value needs a permission, a recent
   MFA code, and is audited.
3. **Database:** the production database, its snapshots, backups and read replicas must be
   encrypted with AWS KMS.
4. **Files:** documents and data exports in S3 must be encrypted at rest with SSE-KMS, in buckets
   that block public access and deny unencrypted or non-TLS requests. Files are downloaded only
   through short-lived pre-signed URLs issued after a permission check.
5. **Other stores:** logs, traces, backups and CI artifacts must be encrypted at rest. Staff
   devices must use full-disk encryption.
6. **Never stored:** ACH files are returned to the caller and never stored; only batch metadata
   is kept. Full-SSN tax form exports are never stored.

### 4. Field keys: envelope encryption with AWS KMS

1. Production must use the AWS KMS key provider; the API refuses to start in production with
   any other (`FIELD_KEY_PROVIDER`, `apps/api/src/config.ts`).
2. Each field key version is a random 256-bit data key generated by KMS and stored only in its
   wrapped form in the `field_keys` table (migration 0030). The app role may only read that
   table. At start, the API asks KMS to unwrap each version and holds the keys in memory only.
3. New values are written with the newest version. Older versions stay readable until every
   value has been re-encrypted.

### 5. Key rotation

| Key                               | Rotation                                                              |
| --------------------------------- | --------------------------------------------------------------------- |
| AWS KMS key that wraps field keys | Automatic annual rotation turned on                                   |
| Field data key                    | At least once a year, and at once if compromise is suspected          |
| Signing key                       | At least once a year, and at once if compromise is suspected          |
| Password pepper                   | Only if compromised (hashes are re-made at the next sign-in)          |
| Third-party API keys and secrets  | At least once a year, when a person with access leaves, or if exposed |
| Database and service passwords    | At least once a year, and when a person with access leaves            |

Field data keys are rotated with the documented procedure (`apps/api/src/security/rotation.ts`):

1. `keys:rotate` adds a new data key version, run as the database owner.
2. The API and workers are restarted so they encrypt with the new version.
3. `keys:reencrypt` rewrites every value still on an older version, in batches, and stops on the
   first value that does not decrypt rather than skip it. It records when the version finished.
4. `keys:status` shows how many values each version encrypts. An old version must not be retired
   until it encrypts nothing.

Each rotation must be recorded in the change log with the operator and the result.

### 6. Who can use keys

1. The KMS key policy must allow `Decrypt` and `GenerateDataKey` only to the IAM roles of the
   API and job workers, and to the role that runs key rotation.
2. Key administration (policy changes, disabling, scheduling deletion) must be limited to a small
   named group approved by the [Security Officer], and must be separate from key use: an
   administrator cannot decrypt.
3. No person may hold standing permission to decrypt with the field key. Any human use is
   break-glass under the [Access Control Policy](access-control-policy.md).
4. Every KMS call is logged in CloudTrail. Disabling a key, scheduling deletion, or changing its
   policy must raise an alert.
5. KMS keys must have deletion protection through a waiting period of at least 30 days, and the
   key must be available in the recovery region (see the
   [Business Continuity and Disaster Recovery Plan](business-continuity-and-disaster-recovery-plan.md)).
   Losing the key makes all field-encrypted data unreadable.

### 7. Secrets management

1. Production secrets must be kept in AWS Secrets Manager (or SSM Parameter Store with KMS) and
   given to the running service at start. They must never be in source code, images, CI logs,
   tickets or chat.
2. AWS access must use IAM roles with short-lived credentials. Long-lived access keys are allowed
   only where a role cannot be used, must be stored as secrets, and must be rotated at least every
   90 days.
3. Secrets in CI must be scoped to the workflow and environment that need them.
4. Committed secrets are blocked by gitleaks in CI. A secret that reaches any repository, log or
   message must be rotated at once and handled as a security incident.
5. The development example key in `.env.example` is public and must never protect real data;
   production and key import both refuse it.

## Roles and responsibilities

| Role               | Responsibilities                                                        |
| ------------------ | ----------------------------------------------------------------------- |
| [Security Officer] | Owns this policy; approves key administrators; reviews rotation records |
| [Engineering Lead] | Implements encryption, runs rotations, keeps the secrets inventory      |
| Key administrators | Manage KMS key policies; cannot use keys to decrypt                     |

## Exceptions

Exceptions must be documented, approved by the [Security Officer], and time-limited. No exception
may allow Restricted data to be stored unencrypted.

## Enforcement

Mishandling keys or secrets may lead to removal of access and disciplinary action. Exposed secrets
are always rotated.
